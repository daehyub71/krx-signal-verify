## 1. 프로젝트 목표

`krx-signal-alerts`가 평일 08:20 KST에 보내는 신호 메일은 **기술적 조건만** 말한다.
선행 프로젝트 `krx-signal-briefing`은 그 신호가 근거를 갖는지 **하루치씩** 검증해 두 번째 메일로 보냈다.
잘 돌았지만 네 가지가 비어 있었다.

```
① 판정을 매일 내면서 그게 분별력이 있었는지 한 번도 세지 않았다
     — 점수가 "보지 않는 것" 목록에 「공시 이후의 주가」가 그대로 남아 있다
② 증거가 세 갈래(공시·뉴스·수급)뿐이라 재무·공매도를 못 본다
③ 상위 신호에 걸린 종목만 볼 수 있다 — 궁금한 종목을 넣어 볼 수가 없다
④ 어제 무슨 판정을 했는지 보려면 메일함을 뒤져야 한다
```

`krx-signal-verify`는 **검증을 계승하고 위 넷을 채운다.**

```
차트 신호 (상위)  또는  사용자가 넣은 임의 종목        ← ③ 신규
      │
      ├─ 1  DART 공시 본문      무슨 일이 있었나
      ├─ 2  네이버 뉴스          왜 그랬나
      ├─ 3  기관·외국인 수급     누가 사고 팔았나
      ├─ 4  재무 (신규)          그 회사는 어떤 상태인가        ← ② 신규
      └─ 5  공매도 (신규)        반대편에 선 돈이 있는가        ← ② 신규
      │
      ▼
  정합 / 불일치 / 무관  + 근거 서술 + 규칙 점수      ← 계승 (판정은 코드가, LLM은 설명만)
      │
      ├─ 저장  판정·점수·구성 요소를 남긴다                    ← ① 신규 (선행은 버렸다)
      ├─ 채점  5·20·60거래일 뒤 주가를 붙여 분별력을 잰다      ← ① 신규
      └─ 표면  간략 메일 + 웹 대시보드                          ← ④ 신규
```

### 이 프로젝트가 하지 않는 것 (비목표)

| 비목표                                           | 이유                                                                                                                   |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **매매 판단** — 매수·매도·보류·진입 시점·목표가·손절             | 선행에서 상속. 근거 정합성 판정까지는 하되 매매 판단은 하지 않는다. 여기가 유사투자자문업 경계다 (R1)                                                         |
| **개별 종목의 미래 예측** — **이 프로젝트에서 새로 생긴 가장 큰 경계** | 적중 추적(§4-2)은 **이 시스템의 판정이 분별력이 있었는지**를 재는 것이지, 「이 종목이 오를 것」을 말하는 장치가 아니다. 둘은 한 걸음 차이라 문구·표면·저장 형태 모두에 방어를 둔다 (R2·N2) |
| **적중률로 가중치를 자동 최적화**                          | 표본이 하루 수십 건이고 시장 국면이 바뀐다. 자동 최적화는 과적합에 더해 **왜 그 점수인지 설명할 수 없게** 만든다 — 점수의 유일한 장점을 버리는 셈이다 (V5·R4)                    |
| **수신자 확장**                                    | `RECIPIENTS`는 본인 1명, 대시보드는 SSO 뒤. 선행 R7 그대로 (R1)                                                                     |
| MCP **서버** 제작 — **비목표가 아니라 「범위 밖」** (V14, 2026-09-02) | **여기서 안 할 뿐, 별도 프로젝트에서 한다.** 이 프로젝트는 남이 만든 MCP 서버를 데이터 소스로 쓰기만 한다. 어느 프로젝트에서 만들지는 **실측 후 판단**한다 (§2-3 V14) |
| LLM에 도구를 쥐어 주는 에이전트 루프                        | 도구 호출 순서는 코드가 정한다. 선행에서 지킨 규칙 그대로 (N5)                                                                               |
| 상위 `krx-signal-alerts` **스크리닝 로직** 수정         | 읽기만 한다. 예외는 dispatch 단계 하나 (계승)                                                                                      |
| 실시간·장중 판정                                     | 하루 1회 배치 + 온디맨드. 장중 변화는 다음 날 반영                                                                                      |
| 카카오톡                                          | 본문 200자에 판정 근거가 들어가지 않는다. 메일과 웹 전용                                                                                   |

> **「비목표」와 「범위 밖」은 다르다** (2026-09-02 사용자 지시).
> 비목표는 **안 한다**는 뜻이고, 범위 밖은 **여기서 안 할 뿐 다른 데서 한다**는 뜻이다.
> 위 표에서 MCP 서버 제작만 후자다 — 나머지는 전부 비목표다.

| **3층 분리 · 노드 20줄 · I/O 노드는 예외를 밖으로 내지 않는다** | 예외가 새면 `record_run`에 못 가 실패 기록까지 사라진다 |
| **금지어에 걸린 서술은 다듬지 않고 버린다** | 사용자 결정 2026-08-30 — 경계를 넓히는 쪽이 더 위험하다 |

#### ✅ V4. 「판정이 맞았다」를 무엇으로 정의하는가 — **이 프로젝트에서 가장 중요한 결정**

`불일치`는 **"근거가 신호와 어긋난다"**이지 **"떨어진다"**가 아니다. 그런데 채점 기준을 "예측이 맞았나"로
두는 순간, 이 프로젝트는 하지 않기로 한 일(예측)을 하는 장치가 된다. 정의가 곧 경계다.

| 안 | 정의 | 얻는 것 | 대가 |
|---|---|---|---|
| **A. 그룹 분별력** **(추천)** | 개별 종목의 맞고 틀림을 따지지 않는다. **`정합`으로 판정한 종목군과 `불일치`로 판정한 종목군의 이후 시장 대비 초과수익 분포가 서로 다른가**를 본다 (중앙값 차이 · 분포 겹침) | 종목별 예측이 되지 않는다. "이 지표에 분별력이 있는가"라는 **시스템 성능** 질문에 머문다 | 표본이 쌓여야 말할 수 있다. 하루 수십 건이면 의미 있는 차이를 보는 데 수개월 |
| B. 개별 적중 | 종목마다 「맞음/틀림」을 매기고 적중률 % | 직관적이고 표본이 적어도 숫자가 나온다 | **사실상 예측 성적표다.** 화면에 「불일치 판정 적중률 68%」가 뜨면 다음 판정을 예측으로 읽게 된다 (R2) |
| C. 채점하지 않음 | 주가만 붙여 보여 주고 집계하지 않는다 | 경계가 가장 안전하다 | ①번 문제를 못 푼다 — 이 프로젝트를 새로 만드는 이유가 사라진다 |

**→ A로 확정.** 관측 구간 **5·20·60거래일**, 기준은 **소속 시장 지수 대비 초과수익** — 시장이 통째로 오른 날을 판정의 공으로 돌리지 않기 위해서다.

**→ A로 확정** (2026-09-02 사용자 결정). 근거는 비용이 아니라 **원칙**이다 —

#### ✅ V13. 콜드스타트 표본을 어떻게 만드는가 — **B안 확정 (2026-09-01)**

F21은 「`ksa_signals`의 과거 신호를 **60~120거래일**분 소급 판정해 추적의 출발 표본을 만든다」고 적었다.
근거는 **「판정은 LLM 없이 코드만으로 나므로 소급이 싸다」**였고, 그 부분은 맞다. 전제가 틀렸다.

```
krx-signal-alerts  .github/workflows 스케줄 워크플로 추가 = 2026-08-17 (git 확인)
                   → ksa_signals 이력 ≈ 10거래일
F21이 요구하는 것   60~120거래일
                   → 없는 신호는 소급할 수 없다
```

이게 막히면 R10의 **「60거래일 지표는 약 3개월 뒤」**가 전혀 완화되지 않는다.

| 안 | 내용 | 얻는 것 | 대가 |
|---|---|---|---|
| A. 과거 신호를 재현한 뒤 판정 소급 | 상위 전략 5개(MTF·눌림목·VCP·스퀴즈·턴어라운드)를 `ksc_bars` **3년치**에 돌려 과거 신호를 만들고, 그 위에 판정을 소급한다. 상위 `scripts/dryrun.py --days 60`이 **이미 같은 일을 한다** | **표본이 즉시 생긴다.** `ksc_bars`에 3년이 있으므로 60거래일 사후 주가도 **이미 존재**한다 — 3개월을 기다리지 않고 M4를 검증할 수 있다 | **V11 이식 범위를 넓혀야 한다** — 지금 범위(`flags`·`routine`·`verdict`·`render`·`corp`)에 전략이 없다. 상위를 라이브러리로 부르면 결합이 생기고, 복사하면 상위 변경과 갈라진다. 그리고 **재현 신호는 실제로 발송된 신호가 아니다**(억제 F10을 거치지 않았다) — 이 차이를 `source`로 구분해야 한다 |
| **B. 실시간 축적만** **(확정)** | 소급을 포기하고 오늘부터 쌓는다. F21을 삭제한다 | 가장 정직하고 가장 싸다. 표본이 **실제 발송된 신호**로만 구성돼 편향이 없다 | **5거래일 지표는 1주, 20거래일은 1개월, 60거래일은 약 3개월.** 그동안 M4는 화면에 「표본 부족(n=…)」만 띄운다 — **분별력 검증이 사실상 3개월 뒤로 밀린다.** M3·§9 #6·#7의 「60거래일 이상 소급 표본」을 함께 고쳐야 한다 |
| C. 둘 다 쌓되 섞지 않는다 | A로 `source='backfill'` 표본을 만들고, 실시간은 `source='batch'`로 쌓는다. **집계는 기본으로 `batch`만** 보고, `backfill`은 따로 본다 | 조기 검증(A)과 편향 없는 본 표본(B)을 **둘 다** 가진다. `source` 분리는 F43에서 이미 하기로 한 일이라 구조가 는 것이 아니다 | A의 대가(이식 범위)를 그대로 지면서 표가 하나 더 생긴다. 화면에 「어느 표본으로 잰 값인가」를 항상 적어야 한다 |

**→ B로 확정** (2026-09-01 사용자 결정). F21은 「하지 않는 것」이 되고, M3 완료 기준과 §9 #6을 실시간 축적 기준으로 다시 썼다.
V11(이식 범위)은 **건드리지 않는다** — 상위 전략 5개를 끌어올 이유가 사라졌다.

**남겨 두는 고려사항 (v1 범위 밖).** 나중에 소급을 다시 꺼낼 때 이 검토를 되풀이하지 않도록 적어 둔다.

| 항목 | 내용 |
|---|---|
| 언제 다시 볼 만한가 | 3개월을 기다린 뒤에도 표본이 얇아 분포가 갈리지 않을 때. 또는 `rules_version`을 크게 바꿔 과거 판정과 비교가 끊길 때 |
| 재료는 이미 있다 | `ksc_bars` 3년치 · 상위 `scripts/dryrun.py --days 60`이 과거 신호 재현을 **이미 한다** |
| 그때 함께 정할 것 | ① 전략 5개를 어떻게 가져올지(복사 / 상위를 라이브러리로 / 상위에 산출 스크립트 추가 → V11 확대) ② 재현 신호는 **억제(F10)를 거치지 않아** 실제 발송분과 집합이 다르다 — `source='backfill'`로 나눠 쌓고 **집계는 기본으로 `batch`만** 본다 (F43과 같은 취급) |
| 지금 미리 해 두는 것 | `ksv_verdicts.source`를 **처음부터 열어 둔다** (`batch` / `ondemand`). 나중에 `backfill`을 더할 때 스키마를 고치지 않아도 된다 |

#### ⏳ V14. MCP 서버를 어느 프로젝트에서 만드는가 — **실측 후 판단**

**이 프로젝트에서는 만들지 않는다**는 것만 확정했다 (§1 — 비목표가 아니라 범위 밖).
어디서 만들지는 **M3이 끝나 읽기 층이 실물로 선 뒤** 정한다.

**왜 지금 정하지 않는가.** 지금 정하면 도구 스키마를 **추측으로** 짜게 된다.
M0~M3에서 `store.py`가 서고 나면 — `ksc_bars` 페이지네이션, `ksa_runs` 게이트 조회,
`ksc_meta` 신선도 판정, 전용 읽기 롤과 정책이 전부 실물이 되면 — 도구를 **실제 함수에서 뽑을 수 있다.**
먼저 만들면 같은 것을 두 번 짓고 나중에 갈라진다.

| 안 | 내용 | 얻는 것 | 대가 |
|---|---|---|---|
| **B. 별도 프로젝트 `krx-data-mcp`** | `ksc_`·`ksa_`·`ksb_`·`ksv_`·(나중에)`kss_`를 다 읽는 **공용 창구**. 다섯 프로젝트가 함께 쓴다 | 범위가 맞는다. 이 프로젝트의 목적이 흔들리지 않는다. MCP 서버 제작을 처음부터 끝까지 온전히 겪는다 | 리포·venv·CI가 하나 는다 |
| **C. 점수화의 `scorer-mcp`에 얹는다** | 점수화 계획서 M7에 이미 MCP 서버 제작이 있다 — 거기에 데이터 도구를 더한다 | 새 프로젝트가 안 는다. 원래 계획된 자리다 | 점수화가 `stock_scorer` 이관 블로커로 **M0도 시작 못 했다.** 그리고 **사실 층과 해석 층이 한 서버에 섞인다** |

**M3 이후에 볼 것** — ① `store.py`의 조회 함수가 몇 개이고 얼마나 재사용 가능한가
② `coverage`·`freshness`가 게이트 로직과 얼마나 겹치나 ③ 그때 점수화가 M0을 시작했는가.

**범위는 어느 쪽이든 작게 잡는다** — `coverage()` + `freshness()` 둘이면 MCP 서버의 전 과정
(stdio 프로토콜 · 도구 스키마 · 오류 처리 · 버전 고정 · 클라이언트 등록 · 계약 테스트)을 다 겪는다.
도구를 열 개 만든다고 더 배우는 것은 없고 유지비만 는다.

**배치는 그 서버를 부르지 않는다** — 선행 D14 v2(`korea-stock-mcp` 콜드스타트 10.9초로 배치에서 제외)를
그대로 잇는다. 만들어도 **대화형 전용**이다.

## 5. 데이터 모델 — 새로 만드는 것 (`ksv_` 접두어 · **6개**)

| 테이블 | 내용 | 키 |
|---|---|---|
| `ksv_verdicts` | 판정 1건 — `d` · `ticker` · `source`(batch/ondemand) · `stand` · `score` · `parts`(jsonb) · `blind_spots` · `rules_version` | PK `(d, ticker, source)` |
| `ksv_evidence` | 그날 그 종목의 증거 — 공시·본문·뉴스·수급·재무·공매도 (jsonb) | PK `(d, ticker)` |
| `ksv_outcomes` | 사후 주가 — `d` · `ticker` · `h5` · `h20` · `h60` · 각 구간의 **지수 대비 초과수익** · `filled_at`. **`baseline` 열은 두지 않는다** — 기준선은 언제나 소속 시장 지수 하나다 (V12) | PK `(d, ticker)` |
| `ksv_discrimination` | 분포 요약 (F24) — 군별 중앙값·사분위·겹침·표본 수 | PK `(as_of, horizon, rules_version)` |
| `ksv_runs` | 실행 기록 — 게이트 판정·신호 수·판정 수·실패 사유 | PK `run_at` |
| `ksv_requests` | 온디맨드 요청 (V8 A안) — `requested_at` · `ticker` · `status` · `result_d` | PK `id` |

**RLS**: 여섯 테이블 모두 RLS를 켜고, **`to anon` 정책은 만들지 않는다.**
다만 **`to ksv_reader` SELECT 정책은 만든다** — 이것이 없으면 대시보드도 0행을 받는다.

> **RLS가 켜진 테이블에 정책이 하나도 없으면 「아무도 못 읽는다」다.**
> PostgreSQL은 그 경우 테이블 소유자·슈퍼유저·`BYPASSRLS` 롤을 뺀 **모든 롤에 0행**을 준다.
> 선행 `ksb_*`가 「정책 없음」으로 잘 도는 이유는 배치가 **service_role(BYPASSRLS)**을 쓰기 때문이고,
> V9는 정확히 그 우회를 버리기로 한 결정이다. 그래서 읽기 롤에는 **명시적 정책이 필요하다.**
>
> ```sql
> create policy ksv_verdicts_read on ksv_verdicts
>   for select to ksv_reader using (true);   -- 여섯 테이블 각각
> ```
>
> `ksv_reader`에 `BYPASSRLS`를 주는 길도 있지만 **쓰지 않는다** — 폭발 반경이 다시 넓어진다.
`to anon` 정책은 어떤 경우에도 만들지 않는다 (§2-2, 선행 2026-08-31 사고).

## 7. 비기능 요구사항

| ID | 요구사항 |
|----|----------|
| **N1** | **문구 규칙** (계승) — 사실과 근거 정합성은 되고 매매 판단은 안 된다. 금지어: `추천` `매수` `매도` `보류` `목표가` `손절` `여력` `이탈` `진입` `비중` · 단독 `없음`. `순매수`·`순매도`·`매수세`·`매도세`는 허용 복합어로 먼저 지우고 검사한다. 공시·뉴스 제목 원문은 예외. 메일·프롬프트·출력 검증 **세 곳**에 같은 규칙 |
| **N2** | **(신규) 적중 문구 규칙** — 개별 종목에 「맞았다/틀렸다」를 쓰지 않는다. 집계에도 `적중률` `승률` `수익률`을 쓰지 않고 **`초과수익 분포`·`분별력`·`표본 수`**로 적는다. 렌더 테스트가 잡는다 |
| **N3** | 모든 공시 항목에 DART 원문 링크 필수 (계승) |
| **N4** | **3층 분리** (계승) — 그래프 층만 LangGraph를 안다. 도메인은 순수 함수(TDD 대상). I/O만 부수효과. **LangGraph를 걷어내도 도메인이 살아 있어야 한다** |
| **N5** | **MCP 서버는 데이터 소스다** (계승) — 도구 순서는 코드가 정하고 LLM에 도구를 주지 않는다. 버전 고정 |
| **N6** | 노드는 20줄 이내. **I/O 노드는 예외를 밖으로 내지 않는다** — 실패 판정은 `finalize` 한 곳. fan-out에는 reducer 필수 (계승) |
| **N7** | 멱등 — PK upsert. **저장은 나눠 보낸다** (선행에서 하루치가 통째로 사라졌다) |
| **N8** | **되살리는 열이 저장하는 열보다 적으면 재실행이 지운다** (계승) — 왕복 테스트로 잠근다 |
| **N9** | 메일 102,400 bytes 이내, 실제 `EmailMessage` 크기로 테스트 |
| **N10** | 시크릿은 `.env`/Secrets에만. **DART 키는 URL 쿼리에 실리므로 예외 메시지에서 URL을 마스킹한다.** 히스토리·로그에 값이 없는지 배포 전 대조 (계승) |
| **N11** | **`ksv_*`에 `to anon` 정책을 만들지 않는다.** 스키마 회귀 테스트로 고정 (선행 사고). **`to ksv_reader` SELECT 정책은 반드시 있어야 한다** — 테스트는 「정책 0개」가 아니라 **「anon 정책 0개 + reader 정책 존재」**를 본다 |
| **N12** | 판정 규칙 변경은 SPEC F표를 먼저 고친다. 코드의 규칙표는 SPEC의 사본이다 |
| **N13** | **LLM 출력은 코드가 검증한다** — 금지어 · 길이 · 입력에 있는 티커 · **우리가 세어 준 건수**. 모델에게 세라고 시키지 않는다 |
| **N14** | 검증 3종: `ruff check .` · `mypy`(strict) · `pytest`. 웹은 `npm run lint` · `npm test` · `npm run build`. 외부 I/O는 전부 mock |
| **N15** | 배포 전 보안 점검 필수 — 보안 리뷰 · 히스토리 시크릿 스캔 · 로그 마스킹 · 워크플로 권한 · **`ksv_*` RLS** (워크스페이스 CLAUDE.md) |
| **N16** | 그래프 구조를 문서로 자동 생성 (`docs/GRAPH.md`). **설계도(`docs/diagrams/*.dot`)는 손그림이라 조용히 낡는다** — 간선을 자동 생성본과 대조한다 (선행에서 셋 다 낡아 있었다) |

## 9. 완료 기준

1. 평일 연속 **5거래일**, 신호 메일 뒤에 검증 메일이 도착 (0건·데이터 지연인 날 포함)
2. `불일치`로 판정된 **모든 건**의 원문 링크를 열어 규칙·본문과 일치하는지 확인 — 오탐 0건이 목표
3. **새 갈래 손검증** — 재무 5종목을 DART 원문과 대조(금융사 1종목 포함), 공매도 5종목을 KRX와 대조
4. 금지어 테스트(N1)·**적중 문구 테스트(N2)**·링크 필수(N3) 통과
5. **트리거 4경로** — dispatch · 예비 cron no-op · `gate_timeout` · **온디맨드 요청 → 1분 내 결과** (V8 A안 시)
6. **판정 저장** — 배치가 도는 날마다 `ksv_verdicts`에 그날 판정이 `parts`·`blind_spots`·`rules_version`과 함께 남고, 멱등 재실행이 열을 지우지 않는다 (왕복 테스트). **소급 표본은 완료 기준이 아니다** (F21·V13)
7. **적중 추적은 시간이 필요하다** — 소급하지 않기로 했으므로(V13) 5거래일 지표는 **첫 주**, 20거래일은 **약 1개월**, 60거래일은 **약 3개월** 뒤에 처음 나온다. 그때까지 화면은 「표본 부족(n=…)」을 정직하게 표시하고, **없는 확신을 만들지 않는다** (R10). M9 완료를 이 대기에 묶지 않는다 — 배치·표면·보안이 서면 닫고, 분별력은 이후 관찰 항목으로 남긴다
8. **두 시스템 대조** — 병행 기간 중 같은 날 선행 브리핑과 새 검증의 판정이 어긋나는 건을 손으로 확인. 어긋나면 원인을 기록한다
9. 검증 3종(파이썬·웹) 통과 · `docs/GRAPH.md` 최신 · **설계도 간선 대조 일치**(N16) · 배포 전 보안 점검 완료(N15)
10. **접근을 두 갈래로 확인한다** — ① `curl -H "apikey: <anon>"` 이 `ksv_*`에 **빈 배열**을 돌려준다 (R3) ② **`ksv_reader` 자격증명으로는 실제로 읽힌다.** ①만 보면 막힌 것을 M7에서야 안다
